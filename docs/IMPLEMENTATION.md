# DJKMDSLegends Website Implementation Guide

This document is the linear implementation plan for the MVP website.

A developer should be able to execute these steps in order and end with a locally runnable, production-shaped MVP aligned with `DESIGN.md`.

## Implementation Rules

- Follow steps in order.
- Do not skip ahead.
- Keep the implementation static-first.
- Do not introduce a custom backend.
- Prefer simple, deterministic solutions over abstractions.
- Keep all copy/content placeholders clearly marked where final business copy is not yet available.
- At the end of each step, verify the acceptance criteria before proceeding.

---

## Step 0 — Initialize the repo and install dependencies

### Files / commands  
- Create the Vite React TypeScript project  
- Install baseline dependencies  
- Verify generated TypeScript/Vite scaffolding  
- Create the target folder structure for the MVP  
- Remove ambiguity before feature work begins  
  
### Commands  

Make sure you're on node 24:

```
nvm use 24
```

From the parent directory where the repo should live:  
  
```bash  
npm create vite@latest djkmd-legends-site -- --template react-ts  
cd djkmd-legends-site  
npm install
```

Optional but recommended linting/tooling install:

```
npm install -D eslint @eslint/js typescript-eslint eslint-plugin-react-hooks eslint-plugin-react-refresh
```

Create the initial folder structure expected by this implementation plan:

```
mkdir -p src/app  
mkdir -p src/components/layout/Header  
mkdir -p src/components/layout/Footer  
mkdir -p src/components/layout/Container  
mkdir -p src/components/layout/Section  
mkdir -p src/components/marketing/Hero  
mkdir -p src/components/marketing/About  
mkdir -p src/components/marketing/Performers  
mkdir -p src/components/marketing/Media  
mkdir -p src/components/marketing/Calendar  
mkdir -p src/components/marketing/BookingForm  
mkdir -p src/components/marketing/MailingList  
mkdir -p src/components/marketing/PressKit  
mkdir -p src/components/shared/Button  
mkdir -p src/components/shared/Heading  
mkdir -p src/components/shared/Card  
mkdir -p src/content  
mkdir -p src/styles  
mkdir -p src/types  
mkdir -p public/assets/images  
mkdir -p public/assets/logos  
mkdir -p public/assets/press-kit
```

Create a Node version pin file:

```
echo "24" > .nvmrc
```

Start the generated app once to verify the scaffold is healthy:

```
npm run dev
```

### High-level explanation

This step establishes the repository using the official Vite React TypeScript template and confirms that all baseline scaffold files already generated by Vite are present and valid.

This is important because the implementation plan assumes the project begins from a known-good TypeScript/Vite baseline rather than from a hand-built custom scaffold.

The Vite React TypeScript template should generate, at minimum, the core files needed for local development and build execution, including:

- `package.json`
- `tsconfig.json`
- `tsconfig.app.json`
- `tsconfig.node.json`
- `vite.config.ts`
- `index.html`
- `src/main.tsx`
- `src/App.tsx`

These generated files should be treated as the initial baseline and then progressively adapted in later steps. Do not hand-roll replacement config files in Step 0 unless there is a concrete reason.

### What should be verified in this step

Confirm that the Vite scaffold has created the following correctly:

#### TypeScript configuration

- `tsconfig.json` exists
- `tsconfig.app.json` exists
- `tsconfig.node.json` exists

#### Vite configuration

- `vite.config.ts` exists

#### App entry files

- `index.html` exists
- `src/main.tsx` exists
- `src/App.tsx` exists

#### Package scripts

Open `package.json` and confirm that scripts exist for at least:

- `dev`
- `build`
- `preview`

### Files to inspect but not yet materially customize

At this step, inspect these files only to verify they exist and are healthy:

- `package.json`
- `tsconfig.json`
- `tsconfig.app.json`
- `tsconfig.node.json`
- `vite.config.ts`
- `index.html`

Do not substantially modify them yet beyond what is necessary to confirm the scaffold is correct.

### Additional notes

- There is no need to manually run `npm init` when using the Vite project generator.
- There is no need to manually install `react`, `react-dom`, or `typescript` separately after using the React TypeScript Vite template, because those are included by the generated scaffold.
- There is no need to manually author `vite.config.ts` or `tsconfig.json` from scratch in the initial step unless the template failed or there is a deliberate architectural deviation.

### Acceptance criteria

- The repo exists as a Vite React TypeScript project.
- `npm install` completes successfully.
- The generated scaffold includes:
    - `tsconfig.json`
    - `tsconfig.app.json`
    - `tsconfig.node.json`
    - `vite.config.ts`
    - `index.html`
    - `src/main.tsx`
    - `src/App.tsx`
- `package.json` contains working `dev` and `build` scripts.
- The target folder structure for the MVP has been created.
- `.nvmrc` exists and pins Node 24.
- `npm run dev` starts successfully using the unmodified scaffold.
- The project is now in a known-good state and ready for Step 1.

## Step 2 — Create shared type definitions and static content models

### Files to create

- `src/types/performer.ts`
- `src/types/site.ts`
- `src/content/performers.ts`
- `src/content/site.ts`
- `src/content/social.ts`

### High-level explanation

This step defines the content model that will drive the MVP. Static, code-owned content should live in structured files rather than being hardcoded inline throughout components.

### What should be in these files

#### `src/types/performer.ts`

Create and export:

```
export type Performer = {  
  id: string;  
  name: string;  
  imageSrc: string;  
  imageAlt: string;  
  shortDescription: string;  
  tags?: string[];  
};
```

#### `src/types/site.ts`

Create types for site-wide content/config such as:

- navigation item
- social link
- CTA link if desired

Keep types small and explicit.

#### `src/content/performers.ts`

Export an array of placeholder performer objects matching the `Performer` type.

Use realistic placeholder entries such as:

- celebrity tribute act names
- placeholder descriptions
- placeholder image paths in `public/assets/images`

#### `src/content/site.ts`

Export core site content/config, e.g.:

- site title
- hero headline
- hero subcopy
- about copy
- booking email label
- press kit path
- section IDs / labels
- YouTube placeholder video ID
- calendar placeholder URL
- booking form endpoint placeholder
- mailing list embed placeholder

#### `src/content/social.ts`

Export placeholder social links:

- Instagram
- Facebook
- YouTube
- TikTok

### Acceptance criteria

- The repo now has centralized content and types files.
- Content can be imported by components without type errors.
- No content-critical strings need to be duplicated across many components later.

- accepts `children`
- optionally accepts `className`
- wraps children in a centered max-width container

- horizontal padding

#### `Section.tsx`

A simple component that:

- accepts `id`

#### `Section.module.css`

- vertical spacing
- section block layout

### Acceptance criteria

- Layout primitives compile without error.
- Developer can wrap content with `Container` and `Section`.

## Definition of Done

The local MVP is complete when all of the following are true:

1. The site runs locally with `npm run dev`.
2. The site builds successfully with `npm run build`.
3. The site is a single-page React TypeScript application.
4. The major sections are present:
    - Hero
    - About
    - Performers
    - Media
    - Calendar
    - Booking
    - Mailing List
    - Press Kit
5. Navigation anchors work.
6. Shared content is centralized.
7. Static assets resolve.
8. Integrations are cleanly stubbed or wired in replaceable ways.
9. No custom backend exists.
10. The implementation is ready for subsequent deployment work.
